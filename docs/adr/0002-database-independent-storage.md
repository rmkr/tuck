# Database-independent storage

The user requires a replaceable database layer. The memory module owns validation, client grants, revisions, retry checks, tokenization, and MCP response formats. A typed storage interface reads records and receipts, runs scoped keyword searches, and commits a memory change with its search terms and operation receipt atomically.

Each adapter must apply scope filtering before ranking and limiting. Search ranks the number of distinct matching terms from highest to lowest, then memory ID from lowest to highest. Each complete read or search holds a shared read guard. Mutations hold an exclusive write guard across validation, receipt checks, record reads, and commit. The read guard covers ranking and every record fetch used to build the result. The Turso adapter serializes access to its single connection internally. An adapter must preserve atomic commits, durability, and this ordering when it replaces Turso.

Turso is the original adapter. Its SQL, schema, connections, file checks, and crash-test hooks stay inside that adapter. Startup chooses the adapter. The existing database format is preserved. Adding another engine requires implementing the storage interface and passing the shared public MCP tests. The SurrealDB adapter and persistent backend selection are recorded in [ADR 0003](0003-per-store-storage-engine.md) and [#9](https://github.com/rmkr/tuck/issues/9).
